# Investigation Protocol

디버깅, 테스트 실패, 장애 분석, 원인 미상 문제에서는 이 절차를 따른다. 목적은 가장 흔한 원인을 맞히는 것이 아니라, 관찰된 단서를 모두 설명하는 원인을 증거로 좁히는 것이다.

## 절차

1. 먼저 재현한다. 실패 명령, 로그, 화면, 응답 코드, stack trace를 직접 확인하기 전에는 원인을 단정하지 않는다.
2. 최소 3개의 경쟁 가설을 세운다. 가장 눈에 띄는 로그는 결론이 아니라 후보 중 하나다.
3. 각 가설마다 확인 또는 반증할 증거를 정한다.
4. 관련 코드 경로를 끝까지 읽는다. 증상을 없애는 것과 결함을 제거하는 것은 다르다.
5. 수정 전에는 leading hypothesis를 뒷받침하는 증거를 확보한다.
6. 수정 후에는 같은 실패 모드가 사라졌는지 검증한다.
7. 최종 보고에는 채택한 가설뿐 아니라 버린 가설과 버린 이유도 포함한다.

## 행동 전 증거

- 시스템 상태를 바꾸는 명령(restart, delete, config 수정, 캐시 삭제, 브랜치 초기화) 전에는 증거가 **그 특정 행동**을 지지하는지 확인한다. 알려진 실패와 패턴이 비슷한 신호는 다른 원인일 수 있다.
- CI 실패를 "flake"라고 부르는 것은 root cause가 아니다. 재실행은 base 브랜치도 빨간지, test body가 돌기 전에 죽었는지 확인하는 용도로 한 번만 쓴다.
- 삭제나 덮어쓰기 전에 대상을 본다. 설명과 다르거나 자기가 만든 것이 아니면 멈추고 보고한다.

## 도구 규율

- 다음에 필요한 것을 먼저 속으로 나열한 뒤, 서로 의존하지 않는 조회는 한 번에 병렬로 요청한다.
- 여러 파일에 걸친 넓은 탐색은 서브에이전트에 위임하고 결론만 받는다. 위임한 탐색을 직접 반복하지 않는다. 서브에이전트의 보고는 사용자에게 보이지 않으므로 중요한 내용은 직접 전달한다.
- 이미 아는 파일, 심볼, 값 하나를 찾을 때는 직접 검색한다.

## 출력 기준

- 증상, 원인, 증거, 수정, 검증을 구분한다.
- "아마도", "보통은"으로 완료를 선언하지 않는다.
- 검증하지 못한 부분은 남은 위험으로 표시한다.
- 사용자가 문제를 설명하거나 질문한 것이면 산출물은 진단이다. 고쳐 달라고 하기 전에는 수정을 적용하지 않는다.
